# Разработка модуля

## Структура

```text
content/exports/         канонические документы из Foundry
data/                    папки, модели ПКТ и производные реестры
runtime/                 код Foundry и общие доменные сервисы
forge/                   Киберпанк-Кузница NPC, каталог и генератор
licenses/                лицензии адаптированного стороннего кода
sheets/                  контроллер вкладки «Хром»
rule-elements/           CyberpunkHumanity
scripts/lib/             общая сборочная логика
scripts/maintenance/     разовые опасные миграции
packs/                   собранные LevelDB-компендиумы
tests/                   unit и pipeline-тесты
assets/icons/            только модульные/авторские изображения
```

Входные файлы Foundry имеют семантические имена:
`runtime/cyberware-runtime.mjs` отвечает за hooks, настройки и миграции,
`runtime/item-sheet-enhancements.mjs` — за улучшения предметов, признаки и
регистрацию Rule Element.

Общая схема имплантов и парсер описаний находятся в
`runtime/cyberware-schema.mjs`. Очереди актёров, каталог ПКТ и расчёт
Человечности разделены на самостоятельные сервисы.

Кузница не хранит копию ассортимента. `forge/catalog.mjs` во время работы
индексирует только `cyberpunk-remaster.cyberpunk-items`, а
`forge/loadout.mjs` подбирает допустимые по уровню документы. Клонирование
сохраняет описание, `img`, Rule Elements, активации, вложенные предметы и UUID
источника. Статблоки, служебные NPC-атаки и записи программ строятся отдельно:
это не новые авторские предметы экипировки.

## Команды

```powershell
npm install
npm run build
npm test
npm run lint
npm run format:check
npm run test:coverage
npm run check
```

- `build` преобразует exports в пакеты, не меняя исходные JSON.
- `validate` сравнивает пакеты с преобразованными exports вплоть до содержимого
  документов, проверяет UUID, публикацию, папки и ПКТ. Пути и файлы иконок
  намеренно не проверяются.
- `audit:pkt` проверяет состав, цены, варианты и типизированные бонусы.
- `test` запускает unit-тесты, validator и аудит ПКТ.
- `test:coverage` строит отчёт покрытия исполняемого JavaScript и требует не
  менее 70% строк, 65% ветвей и 75% функций.
- `check` добавляет lint, format check и чистую сборку.
- `clean:build` оставляет три последние резервные копии deploy. Число меняется
  через `BUILD_BACKUP_RETENTION`.

## API Кузницы

После `init` API доступен как `game.modules.get("cyberpunk-remaster").api.forge`.

- `open(options)` — открыть окно;
- `preview(form)` — получить воспроизводимый предпросмотр без записи;
- `generate(form)` — создать или перестроить одного NPC;
- `generateBatch(form)` — создать группу;
- `refreshInterfaces(actor)` — пересчитать только строку `Устройство:*`;
- `refreshCatalog()` — сбросить кеш и перечитать предметный компендий;
- `createLauncherMacro()` — создать макрос запуска.

Создание и перестройка доступны только GM и только в SF2e. Перестройка сначала
делает резервную копию, а при ошибке удаляет новые документы и восстанавливает
статблок. Кузница вызывает только `reconcileGrantedItems` для выданных
имплантами предметов; `reconcileHumanity` для NPC намеренно не вызывается.

Версии зависимостей зафиксированы в `package-lock.json`. Стиль файлов задают
`.editorconfig`, ESLint и Prettier.

## Источники данных

`content/exports/*.json` — единственный публикуемый текстовый источник
документов. `packs/*` — производный результат сборки. Изменения в Foundry
попадают в exports через `sync:from-foundry`; ручное дублирование одних и тех
же данных в двух местах не требуется.

Трансформации должны быть идемпотентными. Производные флаги разрешены для
структуры ПКТ и состояния экземпляра, но механика обычного импланта читается
из его описания.

## Идентичность документов

Постоянной идентичностью предмета, страницы журнала или макроса считается его
16-символьный Foundry ID (`_id`), а не отображаемое название. Название разрешено
свободно редактировать и переводить. Ссылки, модели ПКТ, миграции и тесты должны
использовать ID или полный UUID.

Поиск по названию допустим только как явно документированный fallback старой
миграции. Новый runtime-код не должен определять вид импланта или его механику по
названию: канонические поля берутся из последнего служебного блока описания.

## Миграции

Миграции актёров задаются отдельными версиями. Новая версия должна:

1. выполнять только своё изменение;
2. быть безопасной при частично изменённых данных;
3. иметь тест перехода с предыдущей версии;
4. не запускать заново старые нормализации.

## Резервные копии и deploy

Перед deploy проверяются блокировки всех LevelDB-пакетов. Если мир открыт,
операция завершается до изменения установленного модуля. Успешный deploy
создаёт датированную копию в `.build/deploy-backups`.

Не удаляйте прочие каталоги `.build`: там могут находиться ручные снимки
внешних библиотек. Автоматическая очистка касается только deploy-backups.
